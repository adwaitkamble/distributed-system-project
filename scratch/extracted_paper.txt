Topic: Distributed Voting System with Leader Election

Introduction

Colleges, organisations, communities and online platforms use voting and polling systems to collect votes from many users and compute a result. The simplest design uses one central server that receives every vote and counts it. It is easy to build, but the whole poll then depends on that one server. If it fails, voting stops, and any vote that was not yet stored can be lost.

A distributed design spreads this work across several connected nodes. The nodes share voting information, and if one of them fails, another can take over coordination, so the system keeps running.

This paper proposes a Distributed Voting System with Leader Election, a small-scale system built to demonstrate core Distributed Systems concepts: inter-node communication, leader election, failure detection, logical clocks, replication and consistent vote aggregation. Several server nodes run together, and one of them acts as the coordinator. When the coordinator fails, the others detect it and elect a replacement using the Bully or Ring algorithm. Lamport logical clocks order distributed events, each vote carries a unique Vote ID so it is never processed twice, and votes are replicated across nodes so they survive node failures. The system uses gRPC for communication and Docker to run the whole cluster on a single computer.

●  Background and Limitations of Existing Systems

Most simple polling applications follow a centralised client-server architecture, where one server receives requests, validates votes, stores them and calculates the result. This is simple to build, but it causes problems when the server fails or when many users vote at once:

•  Single point of failure: A crash caused by a hardware, software or network fault makes the whole poll unavailable until the server is restored.

•  Vote loss: A vote being processed at the moment of failure may never be stored, and no other server holds a copy of the latest voting state.

•  Performance bottleneck: Every request passes through one server, so response time rises as the number of voters grows.

•  Manual recovery: An administrator usually has to restart or restore the server, which adds downtime.

Using multiple nodes removes these problems but introduces new ones. The nodes must agree on which of them coordinates, how events are ordered, how votes are replicated and how the system recovers after a failure. The proposed system is designed around these questions.

●  Motivation

The aim is a polling system that keeps working when one of its nodes fails. Instead of a permanent coordinator, the system lets the remaining nodes choose a new one when the current coordinator becomes unavailable. We use the Bully [12] and Ring [13] algorithms for this because they are the classical election algorithms in Distributed Systems and are part of our syllabus.

Ordering is the second concern. Votes reach different nodes at different times, and the physical clocks on separate machines are never perfectly synchronised. Lamport logical clocks [14] give each important event a logical timestamp, so the nodes can agree on the order of events without relying on physical time.

Recovery is the third. Replicating vote information lets a new coordinator rebuild the latest voting state after a failure, and unique Vote IDs make sure no vote is counted twice. The proposed system therefore shows how communication, leader election, logical clocks, replication and fault tolerance fit together in one reliable polling system.

●  Problem Statement

To design a distributed voting system that automatically detects coordinator failure, elects a replacement using the Bully or Ring algorithm, keeps a consistent order of voting events with Lamport clocks, and recovers the latest voting state from replicated storage without losing or double-counting votes.

●  Objectives

1) To review recent work on leader election, Raft-based consensus, fault tolerance and distributed voting.

2) To implement Bully and Ring election among gRPC-connected nodes running in Docker containers.

3) To order voting events consistently using Lamport logical clocks.

4) To compare Bully and Ring on election time, message overhead and recovery time for 3, 5 and 7 nodes.

●  Scope and Contributions of the Paper

The proposed system is a small-scale system meant for educational and experimental use. It handles crash failures only, where a node stops responding; Byzantine (malicious) behaviour is not considered. Voter authentication, ballot secrecy and advanced security are also outside the current scope. Within this scope, the paper makes the following contributions:

1) Distributed Polling Architecture: Several peer server nodes, one acting as coordinator, communicate through gRPC or socket-based messages (Fig. 1).

2) Bully and Ring Leader Election: Both algorithms are implemented. When the coordinator fails, the remaining nodes start an election automatically and choose a new coordinator without manual intervention.

3) Event Ordering: Votes and other key operations carry Lamport timestamps, giving a consistent order even when messages arrive at different times.

4) Replicated Vote Storage: Vote data is kept on several nodes so the voting state can be rebuilt after a failure, and each vote carries a unique Vote ID to block duplicate processing.

5) Fault Detection and Recovery: Nodes exchange heartbeat messages. A missed heartbeat from the coordinator triggers an election, and coordination moves to the newly elected node (Fig. 2).

6) Performance Evaluation: The system will be tested with 3, 5 and 7 nodes. Election time, message overhead, vote processing time, recovery time, throughput, duplicate votes and lost votes will be measured, and Bully will be compared with Ring.

Literature review

Recent Distributed Systems research on leader election, consensus, fault tolerance, replicated logs and distributed decision-making relates directly to the proposed system, because a distributed poll needs its nodes to coordinate, recover from failures and keep a consistent view of the votes.

Election research covers both the classical Bully and Ring algorithms and newer versions that try to cut message overhead and election time. Consensus research, especially on Raft [15], is relevant because Raft combines leader election with replicated log management, the same two ideas our system relies on. Work on distributed voting itself studies how decisions are made when voters are split across groups, which gives a theoretical view of polling across nodes.

●  Review of Specific Studies

The studies below were chosen because they relate directly to the main parts of the proposed system: leader election, fault tolerance, consensus, replicated state and distributed voting.

A. Leader election [1]–[4]

Patel and Tere [1] propose an election algorithm that exchanges fewer messages than Bully and Ring while recovering better from faults. Alkohali et al. [2] reduce Bully's message traffic by making one node responsible for running the election and giving each node a time span. Frei et al. [3] study election on rings where message contents can be corrupted, and show that their O(n·ID_max) message cost is close to the best possible in that model. Supase and Pansare [4] elect a coordinator that tolerates node failures and security threats instead of simply picking the highest ID.

B. Raft-based consensus [5]–[9]

Kondru and Rajiakodi [5] add proxy leaders to Raft in RaftOptima and report 60% lower latency with up to 25 servers. Bai et al. [6] make Raft Byzantine fault tolerant in RaBFT using secret sharing and a committee that shares the leader's load. Kondru and Rajiakodi [7] also test Raft under node failures and network partitions with a discrete-event simulator. Wang et al. [8] speed up elections in SCRaft by naming a successor leader in advance, and Du et al. [9] let followers call an election when the leader performs poorly.

C. Distributed voting [10], [11]

Filos-Ratsikas and Voudouris [10] analyse how well district-based voting mechanisms choose a winner. Dang and Hwang [11] survey consensus methods across distributed systems, blockchain and voting, tracing the idea from classical voting theory to Paxos and Raft.

Table 1 summarises these studies. Together they show that leader election, fault tolerance, replicated state and consensus are closely linked problems. Raft-based work treats election and log replication as the core of consistent distributed state [5]–[9], while other work continues to refine Bully, Ring and fault-tolerant coordinator election [1]–[4].

●  Research Gap and the Proposed Solution

Existing research solves individual Distributed Systems problems well. Some studies focus on leader election [1]–[4], others on Raft-based consensus and replicated logs [5]–[9], and others on distributed voting [10], [11]. Most concentrate on one algorithm or a specialised setting, such as content-oblivious rings [3] or Byzantine environments [6]. None offers a small, easy-to-follow polling system that brings leader election, failure detection, logical event ordering, vote replication and consistent vote aggregation together in one application.

The proposed system fills this gap. Server nodes communicate over gRPC, and one of them coordinates the poll. Nodes exchange heartbeats to detect failures, and when the coordinator stops responding, the rest run the Bully or Ring algorithm to elect a new one. The new coordinator rebuilds the latest voting state from the replicated vote log, Vote IDs prevent duplicates and Lamport timestamps keep events in order. Each mechanism has one clear job: election handles coordination, Lamport clocks handle ordering and replication handles recovery. Fig. 1 shows the architecture and Fig. 2 shows the failover process.

Election time, message overhead, vote processing time, recovery time, throughput, duplicate votes and lost votes will be measured. This gives an experimental comparison of Bully and Ring while demonstrating practical concepts from the Distributed Systems syllabus.
